# Scrub-preview v2 — спека (согласованная)

Дата: 2026-07-27. Заменяет текущую реализацию (плотные JPEG-спрайты 3 fps).
Статус: на утверждение.

## Идея одним абзацем
Раз в секунду храним отдельный кадр стрима (WebP, 640×360). На таймлайне всегда
показываем ~фиксированное число кадров, а детализация меняется только шагом
выборки при зуме (реже/чаще), вплоть до каждой секунды. Самый грубый (обзорный)
уровень готовим заранее — его открывают все. Остальные уровни зума нарезаются
**лениво**, при первом обращении, и кладутся в кэш на 24ч. Ховер работает по уже
загруженным кадрам, без сетевых запросов.

## Зафиксированные параметры
- **База: 1 fps, 640×360, WebP** (quality 72–78), отдельные кадры. FPS НЕ повышаем.
- **Eager только базовый (обзорный) уровень.** Остальные — lazy.
- **Кэш сгенерированных листов: TTL 24ч.**
- **Окно адаптивное:** ПК — 4 спрайта × 15 = **60 кадров**; мобилка — 2 спрайта × 15 = **30 кадров**.
- **Никакого полного eager-precompute всей пирамиды масштабов.**
- Спрайт: сетка **5×3 = 15 кадров**, ячейка 640×360, лист 3200×1080, формат WebP.

## Слои

### 1. Источник — базовые секундные кадры (всегда есть)
- Ingest (live + backfill) сохраняет **1 fps WebP-кадры**: `frames/<session>/f_%06d.webp`
  (`ffmpeg -vf fps=1,scale=640:360 -c:v libwebp -q:v 75`).
- Это единственный «сырой» слой, персистентный (на томе, вне 24ч-кэша). Из него
  собираются все уровни зума.
- Live: кадры дописываются по ходу эфира; finished: полный набор.

### 2. Базовый (обзорный) уровень — предгенерация
- Самый грубый шаг: весь стрим укладывается в одно окно (шаг = ceil(длительность/кадры_в_окне),
  округлён по лесенке вверх). Его спрайты **генерируются сразу** после появления
  базовых кадров (его открывают все при входе в стрим) и кэшируются.
- На этом предгенерация заканчивается.

### 3. Остальные уровни — ленивая генерация + кэш
- Любой не-обзорный уровень генерится **только при первом обращении** к нему.
- Не открывали уровень — не тратим CPU/диск.
- Результат → дисковый кэш, **TTL 24ч** (повторное обращение к тому же диапазону/масштабу — мгновенно, статикой).

## Масштаб, окна, адресация
- **Лесенка шага (сек):** `1, 2, 5, 10, 20, 30, 60, 120, 300, 600`.
- `framesPerWindow` = 60 (ПК) / 30 (мобилка). `rawStep = visibleDuration / framesPerWindow`,
  округляется **вверх** до ближайшего значения лесенки. Пользователь шаг вручную не задаёт.
- **Гистерезис:** текущий шаг держим, пока расчётное число кадров остаётся в допустимом
  диапазоне — мелкий зум не переключает соседние шаги.
- **Каноничные окна:** `windowDuration = step × framesPerWindow`,
  `windowStart = floor(time / windowDuration) × windowDuration`. Произвольный старт запрещён.
  Пересёк границу окна → клиент берёт листы обоих окон и подгружает недостающее соседнее.
- **Кадр:** `second = windowStart + globalIndex × step` (`globalIndex` 0..framesPerWindow-1).
  `sheetIndex = floor(globalIndex / 15)`, `cell = globalIndex % 15`, `col = cell % 5`, `row = floor(cell / 5)`.
- Ховер использует эти формулы по уже загруженным листам — **без сети**.

## Серверная генерация листа (по запросу)
- Endpoint: `sessionId`, разрешённый `step`, `time` внутри диапазона (+ признак mobile для окна).
  Сервер сам считает `windowStart` и отдаёт мету N листов (4 ПК / 2 моб). Клиент НЕ задаёт
  число кадров, сетку, разрешение, качество, старт окна.
- Cache miss: читаем 15 базовых кадров (подвыборка 1 fps по `step`), собираем полотно 5×3,
  кодируем WebP, пишем во временный путь → **атомарный rename** в кэш.
- **Singleflight:** один и тот же лист (окно+шаг+индекс) генерит только одна задача, остальные ждут её.
- **Worker pool / нативная многопоточность** для WebP — не блокировать event loop.
- Глобальный лимит параллельных задач = `min(4, cpuCount − 1)` (на весь сервер, не на юзера).
- Cache hit — статика, без декодирования исходников.
- **Ключ листа:** `sessionId + previewVersion + step + windowStart + sheetIndex + genAlgoVersion`.

## Дисковый кэш сгенерированных листов
- TTL 24ч, общий лимит **2 ГБ**, очистка раз в 10 мин.
- Сначала удаляем недописанные и просроченные; при заполнении >90% — LRU до 75%.
- Время обращений — в памяти, пакетно на диск; mtime на каждый запрос не трогаем.
- **Базовые 1 fps кадры сюда НЕ входят** (они персистентный источник).
- Finished-стрим: URL с `previewVersion`, `Cache-Control: public, immutable`.
  Live незавершённое окно — короткий TTL, финализируется, когда появились все исходные кадры.

## Клиент
- Одновременно грузит листы текущего окна (сетевой параллелизм = число листов).
  Лист доступен только после `image.decode()`/`createImageBitmap()`.
- Приоритет — лист под курсором; остальные параллельно. После готовности окна —
  предзагрузка соседнего окна в направлении пана. Устаревшие запросы — `AbortController`.
- **Без чёрного при зуме:** предыдущий набор обслуживает ховер, пока новый не готов;
  готовый лист включается сразу, иначе показываем ближайший кадр из старого набора.
- В памяти держим декодированными листы текущего окна + нужные листы соседнего.
  Недавние — сжатым Blob (возврат к диапазону без сети). Лимит по Blob и оценке decoded size;
  при вытеснении освобождаем object URL.
- **Адаптив:** ПК — 4×15; мобилка — 2×15 (меньше памяти/декода).

## Что переделать в текущем коде
- **Ingest (`PreviewWorker`)**: вместо `fps=3 + tile` в JPEG-спрайты → `fps=1` в отдельные
  **WebP-кадры**; плюс предгенерация обзорного уровня. Live + backfill дают одинаковый источник.
- **Новый модуль генерации листов** (по запросу): подвыборка кадров, сборка 5×3, WebP,
  singleflight, worker pool, атомарная запись, дисковый LRU-кэш 24ч/2ГБ.
- **API**: заменить `GET /api/streams/:id/previews` на выдачу меты окна по `(step, time, mobile)`.
- **БД `stream_previews`**: хранит источник (наличие кадров, число, длительность, `previewVersion`),
  а не геометрию спрайтов. Листы адресуются формулой + кэшируются на диске.
- **Фронт `StreamAreaChart`**: оконная загрузка + лесенка шага + гистерезис + decode-gate +
  no-black + предзагрузка + адаптив ПК/моб; ховер — по загруженным листам.
- Старые JPEG-спрайты и `tile`-логика удаляются.

## previewVersion
Строка версии параметров генерации (fps, разрешение, quality, сетка, лесенка шагов, алгоритм
сборки). Меняется при любой правке этих параметров → инвалидирует URL/кэш, immutable-кэш не «залипает».

## Границы (не меняется)
- 1 fps → минимальный шаг = 1 с (достаточно, «секунда к секунде»).
- Twitch хранит VOD 7–60 дней; старше не раскадровать.
- Требуется **персистентный том** под базовые кадры, иначе после рестарта источник теряется.
- Живой край отстаёт ~10 с.
